## Key Implementation Decisions

### 1. Port-Based Streaming (Phase 2 Task 3)
- `chrome.runtime.sendMessage` is request/response only — cannot push deltas.
- Introduced port protocol (`PDF_STREAM_PORT = 'TRANSLATE_PDF_STREAM'`) with message types: `PdfStreamRequest` → `PdfStreamPiece` (multiple) → `PdfStreamDone` | `PdfStreamError`
- Background `initPdfStreamPortListener()` calls `service.translateStream()`, pushes pieces via `port.postMessage`.
- Viewer `sendTranslationBatchStreamed()` opens port, collects pieces via `onPiece` callback, rejects on error → caller falls back to non-streaming.
- `translateParagraphs(pdfUrl, onPiece?)` accepts optional `onPiece` callback. Each prose batch tries streaming first, falls back to non-streaming on error.

### 2. Look-Ahead Scheduler (Phase 3 Task 1)
- `usePdfLookahead` hook watches `translatedPages` Set. When page N is added, enqueues N+1/N+2.
- Priority yielding: re-checks `translatedPages` after every `await`. If viewport hook translates a target first, look-ahead abandons it.
- Cancellation: per-`pdfUrl` token object, flipped on unmount/url-change.
- Results stored in in-memory cache only (`setMemoryCachedPage`), not React state — viewport hook serves from cache on scroll.
- Reaches the background PDF semaphore via `translateParagraphs` → `chrome.runtime.sendMessage` (not direct import of `services/background`, which is a SW-only entry point).

### 3. Classification Cache + Prose Short-Circuit (Phase 3 Task 2)
- `isObviouslyProse(text)` — deterministic heuristic: >= 80 chars, >= 15 words, no LaTeX delimiters, no strong math markers, >= 80% latin ratio, < 10% symbol density. Never classifies math as prose (verified by 10 math examples in tests).
- `classifyCacheKey()`, `getCachedClassification()`, `cacheClassification()` in `cacheManager.ts` — `classify:` prefix isolates from translation cache.
- Integration into `classifyParagraphs()` in `pdfTranslation.ts` is NOT YET DONE — the exported functions are ready for wiring.

### 4. Cross-Page Request Merging (Phase 3 Task 3)
- `translateParagraphsMerged()` in `pdfTranslation.ts` — accepts `MergedParagraphEntry[]` (paragraphs from multiple pages), delegates to existing `translateParagraphs()` pipeline (which already batches on a flat array), tags results with `pageNumber` for routing.
- The existing per-page `translateParagraphs()` is unchanged — viewport path unaffected. Merging is only active when the look-ahead hook explicitly uses `translateParagraphsMerged()`.
- NOTE: `usePdfLookahead.ts` does NOT yet call `translateParagraphsMerged()` — it still calls `translateParagraphs()` per page. The merged function is exported and tested but not wired into the hook.

### 5. 429-Aware Retry (Phase 4 Task 1)
- In `OpenAICompatibleService.fetchWithRetry()`: 429-specific retry branch with `Retry-After` header parsing, exponential backoff (base 1s, cap 30s, 0-500ms jitter), max 3 retries.
- After exhaustion, throws `ApiError(statusCode=429)` with friendly message so the pool's circuit breaker can fail over.
- `__set429DelaysForTest(true)` static method zeros out delays for integration tests (the pool integration tests were timing out at 5s with real backoff).

### 6. Provider-Configurable Batch Size (Phase 4 Task 2)
- `maxBatchChars?: number` and `maxTextGroupCount?: number` added to `ProviderConfig` and `PoolProvider` (optional, 0/undefined = use global default).
- `splitIntoBatches()` now accepts optional `maxTextGroupCount` — flushes when either char budget OR piece count cap is hit.
- Resolution chain in `translateParagraphs()`: `activeProvider?.maxBatchChars || settings.maxBatchChars`.
- `services/background.ts` intentionally unchanged — caller-side resolution.

### 7. Parallelized Download (Phase 4 Task 3)
- `translateAllPages()` rewritten with N-worker pool pattern (default 4 concurrent pages), wrapped in `Promise.allSettled` for per-page error isolation.
- AbortSignal: once aborted, workers finish current page then stop dispatching; function rejects with `AbortError`.
- Serial pdf-lib generation stays in `translatedPdfGenerator.ts` (already serial via `for` loop).
- `usePdfDownload.ts` updated with comments documenting the concurrent/serial split. API compatible.

## Learnings Extracted (This Section)

### Patterns Discovered
- **Port-based streaming for push semantics:** `chrome.runtime.sendMessage` is request/response. Streaming requires `chrome.runtime.connect` port with custom message protocol.
- **Best-effort streaming with non-streaming fallback:** Streaming is a perceived-speed optimization only. Correctness guaranteed by non-streaming fallback. Partial pieces discarded on error.
- **Controlled-promise mock for intermediate state:** Use `new Promise(resolve => { resolveHold = resolve })` to hold a mock at an intermediate point. Capture callbacks, invoke manually inside `act()`, verify state, then resolve.
- **Fake port factory for streaming tests:** `onMessage.addListener`/`onDisconnect.addListener` capturing into arrays, `postMessage` emits via `setTimeout(0)`.
- **`__set429DelaysForTest()` pattern:** Static method on service class to zero out retry delays for integration tests. Avoids fake-timer complexity with async/await + fetch mocks.
- **N-worker pool for concurrent translation:** Workers pull from shared queue via synchronous index bump, wrapped in `Promise.allSettled` for error isolation.

### Gotchas Encountered
- **`mockReset()` needed before `mockImplementation` in nested describes:** Outer `beforeEach` sets `mockResolvedValue([])`. Must `mockReset()` first or the default implementation persists.
- **`chrome.runtime.connect` not in vitest.setup.ts:** Must check `vi.isMockFunction()` and assign `chrome.runtime.connect = vi.fn()` before mocking.
- **429 retry delays break integration tests:** New backoff logic (1s+2s+4s = 7s) exceeds 5s test timeout. Fixed with `__set429DelaysForTest(true)` to zero delays.
- **`vi.waitFor` inside `act(async ...)` deadlocks:** React's async `act` defers effect flushing until the awaited promise settles. Use `await act(async () => { ... await flush(); })` with `setTimeout(0)` instead.

### Context for Next Session
- The PDF viewer is a WXT extension page (NOT a content script) — uses `chrome.runtime.sendMessage`/`connect` (popup-style).
- Translation cache (`pdfTranslation.ts` `memoryCache` + IndexedDB) is independent of pdf.js proxies.
- The pool coordinator (`ProviderPoolCoordinator`) is the single seam covering all 7 translation paths.
